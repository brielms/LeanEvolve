The research ledger

An optional, domain-neutral record of what a long research programme has actually established — built so that no component can overstate it. See the architecture page for the kernel trust boundary this layer records, and the README for setup.

The hard problem in a months-long formal search is not storing results. It is preventing four different kinds of "nearly proved" from being filed as proved — and keeping a crashed run, an exhausted budget, and a superseded claim from all collapsing into the same word.

The ledger's answer is structural rather than procedural: there is no status column anywhere in the schema. Nothing can write a status, so nothing can lie about one.

Why it is a ledger and not a database

One canonical graph holds typed objects, typed connections, and an append-only event stream. Everything a human wants to look at — a goal board, a chronology, a certified proof graph, a prior-art crosswalk, a recovery queue, a status report — is a projection computed from that state. Projections are disposable by design: deleting every one of them loses no authoritative information.

This is the opposite of the usual arrangement, where a status report becomes a second source of truth that quietly disagrees with the first. Here there is only one place a fact can live, and one way it can get there.

Truth has three values and one way in

ValueMeaning
openNo trusted proof or refutation is present. The default, and the honest answer for everything unresolved — including a timeout and an exhausted budget.
provedAn exact proposition has a currently valid kernel_certified event whose receipt binds source, dependencies, toolchain, evaluator, catalog, checkpoint, and axiom policy.
refutedA trusted formal negation, or a trusted refutation bridge, applies.

kernel_certified is the only truth-bearing action in a vocabulary of 52 event actions, and only the authoritative_evaluator may emit it. A research agent, the scratch gateway, the computation checker, and a human researcher all cannot — enforced by authorize() and tested in tests/test_ledger_vocabulary.py.

A refutation needs a bridge

A witness alone never refutes anything. A refutes edge must originate at a formal_claim carrying trust_level: "kernel"; the witness then attaches to that bridge with supports. This is deliberate. "This counterexample disproves the conjecture" is really two premises — the witness, and a proved theorem saying such a witness suffices — and one binary edge cannot honestly carry both. Retracting the bridge's certification returns the target to open.

The verification ladder

Verification is a ladder. A rung is earned, never assigned, and a lower rung is never silently upgraded. The rank column is what dominant_verification_level compares, so a weaker later event cannot demote a stronger earlier one.

RankLevelEarned byDoes not mean
0 untested, elaboration_failed Nothing yet, or a failed elaboration. That the claim is false.
1 scratch_checked An in-memory Lean stream elaborated through the scratch gateway, binding exact source, checkpoint key, environment identity, declaration, and normalized proposition hash. That the declaration is in any candidate, frontier, or maintained file.
2 axiom_policy_audited #print axioms output whose dependencies are within the standard-axiom policy. That anything else about the proof was independently re-checked.
3 authoritatively_evaluated A separate evaluation applied its own source policy, staged the candidate, and produced receipts that load and verify. That the result is promoted or reachable from the maintained frontier.
4 promotion_audited A clean standalone audit accepted a prospective promotion, binding manifest and catalog hashes and the composed declarations. That the promotion has been recorded as active — that is a separate promotion_recorded event.

Concrete proof projects bind these rungs to their own scratch checker, axiom-policy auditor, authoritative evaluator, and promotion gate. The core deliberately names no project layout and no theorem namespace.

What must never imply what

Each dimension is independent, and the vocabulary keeps their value sets disjoint so an overloaded status cannot creep back in. These are the confusions the design exists to prevent:

  • A timeout is operational: timed_out. It is unresolved — never refuted, never failed.
  • An operational run failure does not invalidate a check that already completed. The check, not the turn, is the transaction boundary.
  • Computational evidence — even an exhaustive, independently checked certificate — supports a claim. It is not a kernel theorem.
  • fully_encoded is not proved. Encoding state describes how completely a claim is written down in a formal system, and says nothing about whether it holds.
  • superseded is not refuted. Being replaced is a lifecycle fact; replaying history to an earlier event must still show the old claim active.
  • A citation or a retained PDF does not make a formal claim trusted. source_evidence is its own dimension for exactly this reason.

Authority

Eight actor roles, each with an explicit ceiling. Authority is checked on every event before it commits, and leanevolve-ledger verify re-checks the whole history for events that exceeded their actor's authority.

ActorMayMay not
research_agentPropose claims and relationships, annotate, abandon its own routes, request checks.Certify, promote, declare a computation proved, revise an exact proposition.
lean_scratch_gatewayStore exact source, record elaboration and scratch outcomes, create formal claims for checked declarations.Certify, promote.
authoritative_evaluatorEmit evaluation, certification, materialization, and promotion.—
axiom_auditorEmit axiom-policy outcomes.Certify.
computation_checkerRecord computations and verified certificates.Certify.
human_researcherCreate, annotate, correct metadata, choose spotlights, authorize campaigns.Certify. Assertion is not proof.

Identity and correction

A formal claim's identity is its normalized proposition, not its name.

  • Changing the proposition creates a new object plus an explicit supersedes, specializes, strengthens, or weakens edge.
  • Renaming a declaration without changing the proposition adds an alias (alias_added), not a new claim.
  • A proposition written as def ... : Prop is a formal claim with no proof.
  • A goal does not become a second object once it is proved. kind says what a thing is; being a goal, a spotlight target, or a frontier member is a property and a projection concern.

History is append-only, so a correction adds a new fact naming the event it corrects (correction_recorded) and never rewrites the old one. A retracted connection leaves the current projection and stays in the audit history. An imported event must state whether its original time and ordering are exact, inferred, or unknown — an importer may not launder an unknown ordering into a confident one.

Surviving a crash

A long campaign gets interrupted: a killed turn, a lost machine, an exhausted budget. Verification work that already succeeded must not evaporate because the process around it died. The queue is built from ordinary check objects and lifecycle events rather than an external broker, so a worker crash cannot strand state somewhere the ledger cannot see.

The workers keep Lean itself alive rather than wrapping repeated lean --stdin calls: one lean --server process owns a checkpoint and environment key and elaborates sequential virtual documents. The durable queue stays the source of job truth, which is what lets the service reconcile a crash without consulting a model transcript.

Scratch success surviving a killed turn is the whole point of the durable lifecycle. It is not a shortcut around any later rung of the ladder.

Artifacts: the hash is the identity

Large bytes do not belong in SQLite. They are written to a local store named by digest, verified, and only then referenced from the graph; replication to slower or removable storage happens afterwards and never changes identity. The invariant that makes this safe is that bytes are hashed before they are trusted, and re-hashed whenever a location is verified.

A path is a hint about where some bytes were last seen. It is never a claim about what they are.

Every add, verify, move, archive, and loss is an event, so an artifact that went missing from a removable volume is a recorded fact rather than a silent absence. under_replicated reports what is not yet safely copied, and reverify re-hashes what is claimed to be present.

Integrity and export

verify checks schema and vocabulary binding, foreign keys, the event hash chain, artifact digests, actor authority, and the invariants that keep derived truth honest. Every finding names its subject, so a report can be acted on rather than merely read.

A clean run means the database is internally consistent and that no recorded event exceeded its actor's authority. It does not mean the mathematics is right; that is what the Lean audit is for.

The chain is tamper-evident, not self-authenticating: anyone who can rewrite the database can also recompute the chain. Detection comes from anchoring a head elsewhere, which is what head_signed events and the exported head record exist to support.

Export is deterministic: two databases holding the same history export to the same bytes, because ordering comes from canonical JSON with sorted keys and a fixed row order rather than from insertion order or wall-clock time. That makes an export diffable, archivable, and usable as a rollback bundle. Restore is a faithful reconstruction rather than a re-derivation — rows are written as recorded, keeping event IDs and digests, and the chain is then verified. That is what lets a restored ledger prove it is the same ledger.

Ordering is the increasing event ID. occurred_at is wall-clock information and is never used to decide precedence.

The nine projections

Each carries the exact chain head that produced it. Callers may cache or render these dictionaries freely; deleting them loses no authoritative state.

ProjectionAnswers

active_goal_statusesThe current derived state of each active goal, without the board's presentation.
chronologyWhat happened, in committed event order.
formal_proof_graphWhich certified claims depend on which, from certification events rather than prose.

Using it

The ledger is off until both paths are configured together — a database and a writable content-addressed artifact store: 

mise run configure -- \
  --ledger-database /path/to/research.sqlite3 \
  --ledger-artifacts /path/to/ledger-artifacts

Then inspect or validate it. --database is global and precedes the subcommand; every subcommand accepts --json: 

mise run ledger -- --database research.sqlite3 verify --artifacts ledger-artifacts --deep
mise run ledger -- --database research.sqlite3 head
mise run ledger -- --database research.sqlite3 status
mise run ledger -- --database research.sqlite3 recover
mise run ledger -- --database research.sqlite3 events
mise run ledger -- --database research.sqlite3 show --id <object-id>
mise run ledger -- --database research.sqlite3 export --output export.json
mise run ledger -- --database research.sqlite3 project --output projections/
CommandPurpose
verifyValidate the whole database. --deep re-hashes local artifact bytes.
headShow the chain head — the value to anchor externally.
showShow one object together with its derived state.
eventsList events in committed order.
exportWrite a deterministic export.
projectRebuild every disposable projection into a directory.
statusCanonical current research status.
recoverCanonical interrupted or unpromoted work.

Canonical mutations belong to the tools that produce them, not to ad-hoc SQL, which is why this CLI is almost entirely read-only. A project that has completed cutover lists the workflows that must fail closed under ledger.required_workflows in leanevolve.toml; those workflows then refuse to start unless both the database and a writable artifact store are available.

How the meaning is pinned down

Prose can drift from behaviour, so the semantics are executable. fixtures.py holds golden scenarios, each the hardest version of one real case: work preserved across a killed turn, a refutation that needs two premises, a candidate that both failed and succeeded, a claim replaced without being disproved, and a computation that is valuable without being a theorem. Each scenario declares its expectations and is replayed by the test suite.

The controlled vocabulary itself is frozen and hashed. Unknown terms are rejected by default: a write naming a kind, relation, action, actor, or state outside the model fails rather than silently extending the model. The current vocabulary is leanevolve-ledger-vocabulary-v1, version 1, and covers 13 object kinds, 19 relations, 52 event actions, 8 actors, and 6 independent state dimensions. Its hash is recorded in the database, so a ledger written under a different vocabulary is detected rather than misread.

Limitations

  • The chain proves consistency, not honesty. Whoever can rewrite the database can recompute the chain. The guarantee only becomes meaningful once a head is anchored somewhere the writer does not control.
  • Authority is enforced within the ledger. It constrains what a component may record. It cannot stop someone with direct database access from writing rows and re-deriving hashes.
  • The rungs are only as strong as their adapters. The core does not implement a scratch checker or an evaluator; it records what one reports. A project that binds authoritative_evaluator to something weak gets a weak guarantee with a strong name.
  • Single writer. SQLite is configured for one writer with concurrent readers, so throughput is bounded by that, by design.
  • Restore keeps recorded identity. That is the point, but it also means restore does not re-verify the mathematics — only that the history is the same history.
