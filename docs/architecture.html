LeanEvolve architecture

How an untrusted proposal becomes a scored, replayable formal result — and what each component is and is not trusted to do. See the README for installation and usage, and the ledger page for the research-record layer.

Everything that finds a proof is untrusted. Everything that accepts one is small, pinned, and offline-recheckable. The architecture exists to keep those two sets from touching.

The asymmetry

A language model, driven by ShinkaEvolve, proposes complete Lean files. Those files are input, not evidence. Fitness is assigned only by running Lean over the candidate and reading back — per configured declaration — the set of axioms that declaration actually depends on. An untrusted component can steer the search anywhere it likes; it cannot award itself a single point of credit.

untrusted Discovery

  • ShinkaEvolve parent selection and archive
  • Language-model proposals and prompts
  • Python orchestration, ranking, scheduling
  • The research ledger and its projections
  • Human steering and interpretation

trusted Acceptance

  • The formal statements in the Lake project
  • The configured allowed_axioms policy
  • The toolchain pinned by lean-toolchain
  • Lean's elaborator and kernel
  • The #print axioms receipt parser

The trusted set is deliberately tiny: the kernel driver and receipt parser together are about 170 lines of Python, and everything they conclude is re-derivable offline from the files a run leaves behind.

The gate

The acceptance rule

Implemented in kernel.py. Every Lean invocation for one candidate shares a single timeout budget of kernel.timeout_seconds; once it is exhausted, the remaining invocations report a timeout rather than silently getting more time.

  1. Source policy. validate_candidate enforces the byte limit, exactly one ordered pair of evolution markers, and the banned-construct scan. A violation ends the evaluation with score zero.
  2. Whole-file check. The candidate is written to candidate_check.lean and elaborated. If that exits nonzero, nothing is credited and no goal is even audited.
  3. Per-goal audit. For each configured goal, the candidate is copied and two lines are appended: example : <target_type> := <declaration> followed by #print axioms <declaration>. That file is elaborated on its own. A receipt is collected only when the run exits zero and prints an axiom line naming that exact declaration.
  4. Acceptance. Goals are then settled in configuration order. A goal is accepted when it has a receipt, its reported axioms are a subset of kernel.allowed_axioms, and every name in its depends_on has already been accepted.

The score is the sum of weight over accepted goals. Because the target wrapper and the axiom command are elaborated together, a declaration published under the expected name but proving a different proposition earns nothing.

Diagnosability has a precise limit worth knowing: goal_axioms records a receipt for any goal whose audit run succeeded, including goals then rejected for axiom-policy or dependency reasons. A goal whose audit run itself failed leaves no receipt at all, and its evidence is the lean.log section for that goal.

What the source policy rejects

Scanning happens after comments and string contents are scrubbed, so a banned word inside a comment is not a violation. The scan is case-insensitive and covers:

CategoryMatchedWhy
placeholdersorryAdmits any goal.
placeholderadmitAdmits any goal.
assumption declarationaxiom, constantA candidate must not extend the axiom base it is judged against.
compile-time command#eval, #reduce, #guardCan print text that counterfeits a receipt line.
custom elaboratorelab, macro, syntaxCan redefine what later source means.
foreign implementationextern, foreign, implemented_byMoves the real definition outside Lean.
initializationinitializeRuns code at import time.
run-time tacticrun_tacExecutes arbitrary metaprogram code.
unsafe declarationunsafe, partialEscapes the termination and soundness discipline.

This textual gate is defence in depth, not the decision. It is a word-level approximation of what Lean source can express; the axiom receipt is the check that actually decides.

The repository is one package with three concentric responsibilities. Only the middle one is inside the mathematical trust boundary.

Data flow

A campaign

  1. load_config validates the JSON and anchors every path at the configuration file.
  2. lake build runs once in the Lake project, so an elaboration failure later is the candidate's fault and not the environment's.
  3. create_run_manifest copies the formal inputs into input_snapshot/ and the LeanEvolve sources into tool_snapshot/, verifying each copy's hash, then opens the event log.
  4. ShinkaEvolveRunner proposes candidates. For each one it spawns evaluate.py as a subprocess with --config and --expected-project-sha256.
  5. On exit — success, failure, or interrupt — write_lineage and then finalize_run_manifest record the lineage, final status, and result inventory.

One evaluation

  1. Re-hash the formal project and compare with --expected-project-sha256, so a statement edited mid-run invalidates the evaluation instead of quietly changing the target.
  2. Apply the source policy.
  3. Elaborate the whole candidate; a nonzero exit ends the evaluation with no credit.
  4. Audit each goal in its own Lean run and collect receipts.
  5. Apply the acceptance rule, then write correct.json, metrics.json, feedback.txt, and evaluation_manifest.json.

Cost note: this is one Lean invocation for the candidate plus one per goal, and each audit re-elaborates the full candidate. Model feedback is the tail of the combined log, truncated to 20,000 characters.

What the model is told

Feedback is deliberately blunt about where credit comes from. It opens with the accepted goal names and the axiom policy, then appends the elaborator output:

This is the real output of mise run demo on the bundled example, whose seed proves one configured goal and leaves the other absent: 

KERNEL-ACCEPTED GOALS: zero_right. Only listed declarations receive fitness credit.
AXIOM POLICY: Classical.choice, Quot.sound, propext
=== candidate ===

=== zero_right ===
'Evolved.zero_right' depends on axioms: [propext]

=== addition_commutes ===
candidate_audit_addition_commutes.lean:18:41: error(lean.unknownIdentifier):
  Unknown identifier `Evolved.addition_commutes`
candidate_audit_addition_commutes.lean:19:14: error(lean.unknownIdentifier):
  Unknown constant `Evolved.addition_commutes`

Note what the second goal produces: a named, located elaboration error rather than a score of zero with no explanation. The model's next turn sees exactly which declaration is missing, and propext — a real dependency of the accepted proof — is inside the configured policy, so the first goal earns its weight.

Isolation of a Lean run

Each invocation runs with cwd set to the Lake project and an environment reduced to only ELAN_HOME, HOME, LANG, LC_ALL, PATH, TMPDIR, and USER. When kernel.warning_as_error is set, -DwarningAsError=true is added. A configured kernel.sandbox_prefix is prepended to the command line, which is how an external sandbox is attached.

Replay

leanevolve-replay --run-dir <dir> re-derives results without contacting a model. It verifies the event chain, the recorded result inventory, and the lineage hashes; confirms the installed LeanEvolve sources match the recorded tool snapshot; then copies input_snapshot/ to a temporary directory, rebuilds it with lake build, and re-evaluates every gen_N/main.lean. On success it prints one line: 

Replay accepted: inventory, lineage, and kernel results agree.

Any error is printed as ERROR: <detail> and the process exits 1.

What replay compares

Re-checked against a fresh kernel runRecorded, but not re-checked
event-chain hashes, result inventory, lineage and node hashes, tool-snapshot identity, candidate file record, accepted_goals goal_axioms, formal_inputs_sha256, lean_toolchain, allowed_axioms, metrics

So replay answers "do the same candidates still earn the same goals here", not "was the original machine honest about its toolchain". The second question is what the recorded hashes are for, and it needs an auditor who already trusts the manifest.

Current limitations

Stated plainly, because a system whose selling point is honest accounting has to be honest about itself.

  • Replay requires a lineage file. A run that ended before ShinkaEvolve created its database has no proof_lineage.json, and replay reports missing proof lineage without checking anything else.
  • Replay is version-locked. It compares the recorded tool snapshot against the installed package rather than executing the snapshot, so replay needs the same LeanEvolve version that produced the run.
  • The textual policy is an approximation. It reduces obvious shortcuts; it is not a complete account of what Lean source can express. The axiom receipt is the decisive check.
  • warning_as_error includes linters. With it enabled, a correct proof carrying a style-linter warning is rejected.
  • Not a host sandbox. Lean elaboration can execute code at compile time. A timeout and a reduced environment are not containment; run untrusted campaigns in a disposable container or virtual machine, and see SECURITY.md.
  • Hashes are tamper-evident, not tamper-proof. They detect edits relative to a manifest an auditor already trusts; on their own, against an adversary who can rewrite the manifest too, they establish nothing.
  • A green build is not a true document. mise run docs proves every link resolves. No gate checks whether this page's prose still matches the code.
