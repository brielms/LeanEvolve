LeanEvolve architecture

How a model proposal becomes a scored, replayable formal result — and what each component is and is not trusted to do. See the README for installation and usage.

The asymmetry

ShinkaEvolve and the language model propose complete Lean files. Those files are untrusted input. Fitness is assigned only by running Lean over the candidate and reading back, per configured declaration, the set of axioms that declaration depends on. An untrusted component can steer the search anywhere; it cannot award itself a point of credit.

untrusted Discovery

  • ShinkaEvolve parent selection and archive
  • Language-model proposals and prompts
  • Python orchestration, ranking, scheduling
  • Human steering and interpretation

trusted Acceptance

  • The formal statements in the Lake project
  • The configured allowed_axioms policy
  • The toolchain pinned by lean-toolchain
  • Lean's elaborator and kernel
  • The #print axioms receipt parser

The acceptance rule

Implemented in kernel.py. A candidate is first checked as a whole; if that run exits nonzero, nothing is credited. Otherwise each configured goal is audited in a separate Lean run, and goals are considered in configuration order:

  1. Lean must elaborate example : <target_type> := <declaration> in the audit module, binding the configured proposition to the candidate declaration;
  2. a receipt must exist for the goal's declaration — that same audit run exited zero and printed a #print axioms line for the exact name;
  3. the reported axioms must be a subset of kernel.allowed_axioms;
  4. every name in the goal's depends_on must already have been accepted.

The score is the sum of weight over accepted goals. Receipts are recorded in goal_axioms even for goals that then fail step 2 or 3, so a rejection remains diagnosable.

The target wrapper and axiom command are elaborated together. A declaration under the expected name but with a different proposition therefore receives no credit.

Data flow

leanevolve-run

  1. load_config validates the JSON and anchors every path at the config file.
  2. lake build runs once in the Lake project, so elaboration failures are the candidate's, not the environment's.
  3. create_run_manifest copies the formal inputs into input_snapshot/ and the LeanEvolve sources into tool_snapshot/, verifying each copy's hash, then opens the event log.
  4. ShinkaEvolveRunner proposes candidates. For each one it spawns evaluate.py as a subprocess, passing --config and --expected-project-sha256.
  5. On exit — including failure or interrupt — write_lineage then finalize_run_manifest record the lineage, final status, and result inventory.

leanevolve-evaluate (one candidate)

  1. Re-hash the formal project and compare against --expected-project-sha256, so a statement edited mid-run invalidates the evaluation instead of silently changing the target.
  2. validate_candidate applies the textual policy.
  3. Elaborate the whole candidate. A nonzero exit ends the evaluation with no credit.
  4. For each goal, append #print axioms <declaration> to a copy of the candidate and elaborate again, collecting the receipt.
  5. Apply the acceptance rule, then write correct.json, metrics.json, feedback.txt, and evaluation_manifest.json.

Cost note: this is one Lean invocation for the candidate plus one per goal, and each audit re-elaborates the full candidate.

Replay

leanevolve-replay --run-dir <dir> re-derives results without contacting a model. It verifies the event chain, the recorded result inventory, and the lineage hashes; confirms the installed LeanEvolve sources match the recorded tool snapshot; then copies input_snapshot/ to a temporary directory, rebuilds it with lake build, and re-evaluates every gen_N/main.lean. On success it prints a single line: 

Replay accepted: inventory, lineage, and kernel results agree.

Any error is printed as ERROR: <detail> and the process exits 1.

Current limitations

  • Replay requires a lineage file. A run that ended before ShinkaEvolve created its database has no proof_lineage.json, and replay reports missing proof lineage without checking anything else.
  • Replay is version-locked. It compares the recorded tool snapshot against the installed package rather than executing the snapshot, so replay requires the same LeanEvolve version that produced the run.
  • The textual policy is an approximation. It reduces obvious shortcuts; it is not a complete account of what Lean source can express. The axiom receipt is the decisive check.
  • warning_as_error includes linters. With it enabled, a correct proof carrying a style-linter warning is rejected.
  • Not a host sandbox. Lean elaboration can execute code at compile time. Timeouts and a reduced environment are not containment; see SECURITY.md.
  • Hashes are tamper-evident, not tamper-proof. They detect edits relative to a manifest an auditor already trusts; they establish nothing on their own without an external anchor.
